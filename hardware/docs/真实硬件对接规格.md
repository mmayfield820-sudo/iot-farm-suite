# 真实硬件（BearPi + E53_IA1）对接规格

> 本规格以 GitHub 仓库 `iot-farm-suite` **basic 分支**已冻结的协议为准，三处权威来源（内容一致）：
> 
> - `contracts/mqtt-topics.md` —— 协议定义
> - `backend/app/mqtt.py` —— 后端真实订阅代码（以此为准，前端模拟器不可靠时以代码为准）
> - `device-simulator/simulator.py` —— 后端提供的参考客户端实现
> 
> 硬件固件请照本文件实现，不要发明新格式。

## 0. 一句话结论

真实板子 = 一台 MQTT 客户端，用**UUID**当身份，往 `sensor/{UUID}/data` 发温度/湿度，订阅 `sensor/cmd` 控制马达，回执到 `sensor/ack`。板子原生的 `{"Temp","Hum","Lux","Motor","LED"}` 格式**不能直接发**，必须翻译成下面的协议字段。

## 1. 身份体系（重要）

| 概念              | 示例                                     | MQTT 里用不用                      |
| --------------- | -------------------------------------- | ------------------------------ |
| `device_uuid`   | `3b8dcefd-3a51-4adc-b452-47c184c0951d` | ✅ **唯一身份**，topic 和 payload 都用它 |
| `device_code`   | `P001-TEMP`                            | ❌ 只作展示/运维核对，不进 MQTT            |
| 数据库 `device_id` | `D001`                                 | ❌ 只在 HTTP 接口里出现                |

- 后端收到消息时强制用 `UUID(value)` 校验 deviceId，**不是合法 UUID 直接拒收**。
- topic 里的 UUID 必须等于 payload 里的 `deviceId`，不一致拒收。
- 板子固件里**硬编码**一个已登记的 UUID 即可（不存在模拟器"换机变 UUID"的问题）。

现有 6 台设备的 UUID（`device.device_uuid`，来自 basic 分支 `004_device_uuid_migration.sql`）：

| device_code  | device_type   | device_uuid                            |
| ------------ | ------------- | -------------------------------------- |
| `P001-TEMP`  | `temperature` | `3b8dcefd-3a51-4adc-b452-47c184c0951d` |
| `P001-MOIST` | `humidity`    | `814621f7-2561-49ad-9766-72d3fcd18d86` |
| `P001-IRRIG` | `irrigation`  | `435106ba-01e7-4745-9646-3907d15b28df` |
| `P002-TEMP`  | `temperature` | `5b0a7464-a7db-449b-ae30-26063977c708` |
| `P002-MOIST` | `humidity`    | `f2ac7d43-6c0d-4fb3-9b1a-5404bc51299a` |
| `P002-IRRIG` | `irrigation`  | `b4d49779-b744-4096-898a-433b2d231839` |

> 真实板子可以**复用**上面某个 UUID（当作这台设备），也可以**新建** UUID 后走 REST 登记（见第 6 节）。推荐先复用 P001 三台的 UUID 联调。

## 2. Broker 与订阅

| 项           | 值                                                              |
| ----------- | -------------------------------------------------------------- |
| MQTT Broker | `8.137.105.88:1883`（云上 EMQX，匿名连接）                              |
| 本地调试备用      | `127.0.0.1:1883`                                               |
| 后端订阅的 topic | `sensor/+/data`、`sensor/state`、`sensor/heartbeat`、`sensor/ack` |

板子需要：

- **发布**到 `sensor/{UUID}/data`（温度/湿度）
- **订阅** `sensor/cmd`（控制指令）
- **发布** `sensor/ack`（控制回执）
- 可选发布 `sensor/state`、`sensor/heartbeat`（让后端知道设备在线）

## 3. 数据上报（温度 / 湿度）

Topic：`sensor/{设备UUID}/data`

### 温度消息（device_type=temperature）

```json
{
  "temperature": 25.6,
  "deviceId": "3b8dcefd-3a51-4adc-b452-47c184c0951d",
  "timestamp": 1787625267746,
  "msgId": "1787625267746"
}
```

### 湿度消息（device_type=humidity）

```json
{
  "plot_moisture": 62.5,
  "deviceId": "814621f7-2561-49ad-9766-72d3fcd18d86",
  "timestamp": 1787625267746,
  "msgId": "1787625267746"
}
```

| 字段                              | 必填  | 说明                                                                       |
| ------------------------------- | --- | ------------------------------------------------------------------------ |
| `temperature` 或 `plot_moisture` | 是   | **二选一，恰好一个**（见第 5 节硬约束 ①）                                                |
| `deviceId`                      | 是   | = topic 里的 UUID                                                          |
| `timestamp`                     | 是   | Unix 毫秒时间戳（13 位数字）                                                       |
| `msgId`                         | 是   | 1–100 字符、每次唯一（参考实现用 `str(毫秒时间戳)`），后端按 `(device_id, message_id)` 去重，重复的丢弃 |

## 4. 控制（灌溉马达）

### 板子订阅：`sensor/cmd`

后端下发格式（deviceId=灌溉设备 UUID，即 `device_type=irrigation` 的那台）：

```json
{"seq": 10001, "ts": 1787625500000, "deviceId": "435106ba-01e7-4745-9646-3907d15b28df", "switch": "on"}
```

| 字段         | 说明                  |
| ---------- | ------------------- |
| `seq`      | 全局递增指令序号，板子回执时要原样带回 |
| `ts`       | 指令生成时间，毫秒           |
| `deviceId` | 灌溉设备 UUID           |
| `switch`   | `on` / `off`        |

板子收到后：控制 E53_IA1 马达 → **必须回执**到 `sensor/ack`：

```json
{
  "seq": 10002,
  "cmdSeq": 10001,
  "action": "control",
  "deviceId": "435106ba-01e7-4745-9646-3907d15b28df",
  "result": "ok",
  "switch": "on",
  "name": "P001-IRRIG"
}
```

| 字段         | 说明                           |
| ---------- | ---------------------------- |
| `seq`      | 回执自己的序号（随便一个递增数）             |
| `cmdSeq`   | **= 收到指令的 `seq`**，后端靠它匹配灌溉记录 |
| `action`   | 固定 `control`                 |
| `deviceId` | 灌溉设备 UUID                    |
| `result`   | `ok` / `failed`              |
| `switch`   | 实际执行结果 on/off                |
| `name`     | 设备名（可选，仅日志）                  |

> ⚠️ **不回 ack = 灌溉记录永远 pending，30 秒后后端判 `timeout` 并产生 `irrigation_failed` 告警。** 这一步必须实现。

## 5. E53_IA1 字段映射与硬约束（最容易踩坑）

### 字段映射

| 板子原生            | 协议字段            | 去向                                        |
| --------------- | --------------- | ----------------------------------------- |
| `Temp`          | `temperature`   | 温度消息                                      |
| `Hum`（**空气**湿度） | `plot_moisture` | 湿度消息（语义妥协：数据库字段就叫 plot_moisture，0–100 符合） |
| `Lux`           | ❌ 无对应           | 协议不接收，先丢弃（如需上报找队长扩展协议）                    |
| `Motor`         | 控制目标            | 订阅 `sensor/cmd` 后控制                       |
| `LED`           | ❌ 无对应           | 协议不接收，先丢弃                                 |

### 硬约束

1. **一条遥测消息只能有一个业务字段**。后端 `_parse_telemetry_value` 检查"恰好一个 metric"，同时带 `temperature`+`plot_moisture` 直接拒收。板子必须把温度、湿度**拆成两条消息**发到各自的 topic。
2. **温度+湿度必须 30 秒内配对**（同一 `plot_id`）才写 `plot_report`。只到一条 → 30 秒后产生 `device_fault` 告警。所以板子读一次应连续发两条（温度+湿度）。
3. **`deviceId` 必须是合法 UUID**，且 topic UUID = payload deviceId。
4. **湿度必须 0–100**，超过拒收。空气湿度天然符合。
5. **`msgId` 每次唯一**，重复的直接被去重丢弃。

### 建议的上报节奏

每次循环（如每 10 秒）：

1. 调 `e53ia1service` 读一次 → 得到 `{"Temp","Hum","Lux","Motor","LED"}`
2. 立即发温度消息（`sensor/{温度UUID}/data`，温度值）
3. 立即发湿度消息（`sensor/{湿度UUID}/data`，湿度值）
4. 可选：发 `sensor/state`（`{"seq","ts","deviceId","switch","reason":"heartbeat","values":{}}`）让后端更新在线状态

## 6. 设备登记（如需新增设备，REST API）

后端 REST 接口（`backend/app/main.py`，FastAPI，需登录 token）：

- `POST /api/devices`：body `{"deviceNo":"HW-TEMP-01","deviceUuid":"<新建UUID>","type":"temperature","plotId":"P001"}`；`type` 只能是 `temperature`/`humidity`/`irrigation`，`deviceUuid` 必须合法 UUID
- `POST /api/devices/{Dxxx}/bind`：body `{"plotId":"P001"}` 绑定地块
- `POST /api/devices/{Dxxx}/commands`：body `{"action":"irrigation_on","activationType":"manual"}` —— 前端/测试触发控制，后端经 MQTT 下发

> 联调阶段直接复用第 1 节 P001 三台设备的 UUID，可以跳过登记。

## 7. 参考实现

- 参考客户端：`device-simulator/simulator.py`（Python + paho-mqtt，后端已写好，照抄 payload 格式）
- 板子原生读法：E53_IA1 驱动 `hdf_e53_ia1`，JS API `e53ia1service`，命令 Start/Read/SetMotor/SetLight，读一次返回 `{"Temp":%.2f,"Hum":%.2f,"Lux":%.2f,"Motor":"ON"/"OFF","LED":"ON"/"OFF"}`
- 官方测试 App：`Micro_E53.hap`（源码在 `bearpi-hm_micro_app` 仓库 `code/Micro_E53`）

## 8. 板子固件实现步骤（给硬件同学）

1. 搭环境烧官方固件 + 装 `Micro_E53.hap`，屏幕确认能读温/湿/光、能点按钮控马达。
2. 确认板子联网方式（WiFi），能访问外网。
3. 改 E53 JS 应用：调 `e53ia1service` 读数据。
4. 写 MQTT 客户端（OpenHarmony 自带/移植 paho），连 `8.137.105.88:1883`。
5. 温度值 → 发 `sensor/3b8dcefd-…/data`（含 deviceId/timestamp/msgId）。
6. 湿度值 → 发 `sensor/814621f7-…/data`。
7. 订阅 `sensor/cmd`，收到 switch 控制马达，回 `sensor/ack`。
8. 联调验证：EMQX 管理台 `http://8.137.105.88:18083`（admin/public）看 topic 消息 → 后端日志/数据库 `plot_report` 出数 → 控制后 `irrigation_record` 变 success。
