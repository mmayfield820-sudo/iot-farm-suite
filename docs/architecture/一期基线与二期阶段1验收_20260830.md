## 4. MQTT 基线

| Topic | 方向 | 当前用途 |
|---|---|---|
| `sensor/{deviceUuid}/data` | 模拟器 → 后端 | 温度或土壤湿度遥测 |
| `sensor/state` | 模拟器 → 后端 | 单设备通信/工作状态快照 |
| `sensor/heartbeat` | 模拟器 → 后端 | 全量设备心跳快照 |
| `sensor/cmd` | 后端 → 模拟器 | 控制和查询指令 |
| `sensor/ack` | 模拟器 → 后端 | 控制 ACK 和查询响应 |

- MQTT 的 `deviceId` 实际表示 `device.device_uuid`，不是数值主键或 `D001` 业务编号。
- 后端在下发灌溉控制前创建 `irrigation_record`，将 MQTT `seq` 字符串化后保存到 `command_id`。
- 模拟器 ACK 的 `cmdSeq` 与 `irrigation_record.command_id` 匹配；只有匹配 ACK 到达后记录才从 `pending` 变为 `success/failed`，超时则变为 `timeout`。
- `switch=on/off` 映射为 `device.work_status=running/stopped`；通信状态仍使用 `device.status=online/offline`。
- 当前后端控制报文实际由 `seq`、`ts`、`deviceId`、`switch` 标识控制，未发送 `action=control`；模拟器 ACK 使用 `action=control`。`contracts/mqtt-topics.md` 中控制请求示例与此处存在差异，已作为阶段 0 基线问题记录。
- 灌溉设备业务 Payload 留空是当前约定：它不能定时向 `sensor/state` 上报写死状态；状态由本地/远程开关变化及心跳快照产生。

JavaFX 目录只有 JAR、使用文档和持久化配置，无法进行源码级检查。本次启动 JAR 后未观察到它连接本地 EMQX，推测其保存的 Broker 配置与本地环境不一致；因此 MQTT 自动化闭环使用严格遵循当前协议的单次 ACK 测试探针完成。测试结束后已删除探针产生的 4 条测试灌溉记录，并恢复设备状态。
