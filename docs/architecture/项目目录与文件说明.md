# 智慧农业项目目录与文件说明

## 1. 这份文档解决什么问题

本项目由 6 人协作完成。大家可以分别开发前端、后端、模拟设备和智能体，但最后这些部分必须能够连接起来。

因此，我们先约定：

- 每类代码放在哪里；
- 每个文件负责什么；
- 哪些文件是团队共同遵守的“接口约定”；
- 哪些目录现在必须创建，哪些目录可以后续再补。

简单来说：**目录是分工边界，契约文件是连接各部分的共同语言。**

## 2. 推荐的项目目录

```text
IoT-farm-suite/
├── docs/                         # 项目说明和设计资料
├── contracts/                    # 前后端、设备端共同遵守的接口格式
├── frontend/                     # 网页前端
├── backend/                      # 后端服务
├── device-simulator/             # 模拟温度、湿度、灌溉设备
├── ai-service/                   # 智能问答和 RAG 服务
├── database/                     # 数据库表结构和初始数据
├── infra/                        # Docker、EMQX、Nginx 等部署文件
├── tests/                        # 联调和集成测试
├── .env.example                  # 环境变量示例
├── README.md                     # 项目总说明
└── CONTRIBUTING.md               # 团队协作规则
```

## 3. 根目录文件

### `README.md`

这是项目的“首页说明”。新成员或老师打开项目后，首先看这个文件。

应该写：

- 项目是做什么的；
- 系统由哪些部分组成；
- 如何启动项目；
- 当前已经完成了什么；
- 每个部分由谁负责。

它的作用是让别人不用询问组员，也能快速运行和理解项目。

### `CONTRIBUTING.md`

这是团队协作规则，不是业务代码。

建议写清楚：

- 分支和提交代码的规则；
- 哪些目录由谁负责；
- 修改接口前需要做什么；
- 如何命名文件、接口和数据库字段；
- 如何进行代码审查和联调。

它可以减少“前端等后端”“后端改了字段但没通知前端”等问题。

### `.env.example`

这是配置示例文件，用来说明项目需要哪些配置，例如：

```text
DATABASE_URL=数据库连接地址
MQTT_HOST=EMQX 地址
MQTT_PORT=1883
AI_SERVICE_URL=智能体服务地址
```

这里不放真正的密码。每个人复制一份为 `.env`，再填写自己的本地配置。这样密码不会被提交到 Git。

## 4. `docs/`：项目资料目录

这个目录存放“怎么设计、怎么部署、怎么使用”的文档，不存放程序代码。

建议分类如下：

```text
docs/
├── requirements/                 # 需求和功能说明
├── architecture/                # 系统架构、模块关系、数据库设计
├── api/                         # API 使用说明
└── mqtt/                        # MQTT 部署和调试说明
```

当前已有的文件可以逐步移动或复制到这里：

- `docs/requirements/01_智慧农业_基本功能清单.md`：说明要实现哪些功能；
- `contracts/mqtt-topics.md`：说明设备如何发数据、接收指令；
- `docs/mqtt/EMQX部署与同步说明.md`：说明如何启动和使用 EMQX。

这些文档回答的是“系统应该做什么”和“系统应该怎样约定”，不是具体代码实现。

## 5. `contracts/`：最重要的接口契约目录

这个目录是 6 人协作的核心。契约就是“大家先约定好格式，再各自开发”。

```text
contracts/
├── openapi.yaml                 # REST API 的统一定义
├── websocket-events.md          # 前端实时消息格式
├── mqtt-topics.md               # MQTT 主题和消息格式
├── data-dictionary.md           # 字段、单位、枚举值说明
└── error-codes.md               # 统一错误码
```

### `openapi.yaml`

规定前端如何调用后端，例如：

- 登录接口；
- 查询地块和设备；
- 查询历史温湿度；
- 下发灌溉指令；
- 查询告警；
- 发送智能问答消息。

前端可以按照它写请求代码，后端可以按照它写接口。接口字段发生变化时，应先修改这个文件并通知团队。

### `websocket-events.md`

规定后端如何把实时变化推送给前端，例如：

- 温度或湿度更新；
- 设备上线或离线；
- 灌溉指令执行成功或失败；
- 新告警产生。

没有这个文件时，前端和后端很容易对“事件名称”和“字段名称”产生不同理解。

### `mqtt-topics.md`

规定设备和后端之间如何通信。当前已有的 `contracts/mqtt-topics.md` 就属于这类内容。

例如：

```text
farm/telemetry/{deviceId}       # 设备上报温湿度
farm/status/{deviceId}          # 设备上报心跳
farm/command/{deviceId}         # 后端下发灌溉指令
farm/command_result/{deviceId}  # 设备回传执行结果
```

模拟设备和真实硬件必须使用相同主题和 JSON 格式，这样更换硬件时后端不用重写。

### `data-dictionary.md`

解释字段的含义、类型、单位和允许值。例如：

- `temperature` 的单位是摄氏度；
- `humidity` 的单位是百分比；
- 设备状态只能是 `online` 或 `offline`；
- 指令状态只能是 `pending`、`success`、`failed`、`timeout`。

它相当于项目的“词典”，避免同一个概念被写成多个名字。

### `error-codes.md`

规定接口出错时返回什么编号和提示，例如设备不存在、没有权限、指令超时等。

前端可以根据错误码显示正确提示，后端也不会每个人随意编写一套错误格式。

## 6. `frontend/`：网页前端

前端负责页面展示和用户操作，不直接连接数据库，也不直接连接 MQTT。

```text
frontend/
├── src/
│   ├── api/                      # 调用后端接口
│   ├── views/                    # 页面
│   ├── components/               # 可重复使用的页面组件
│   ├── stores/                   # 登录用户和页面状态
│   ├── router/                   # 页面路由
│   └── types/                    # 接口数据的 TypeScript 类型
└── README.md
```

- `api/`：集中放请求函数，接口地址以 `contracts/openapi.yaml` 为准；
- `views/`：放完整页面，例如农场总览、设备管理、告警记录；
- `components/`：放温湿度卡片、趋势图、设备状态灯等可复用组件；
- `stores/`：保存登录信息、当前农场、实时数据等共享状态；
- `types/`：定义接口返回的数据格式，防止字段拼写错误。

前端成员可以先使用 Mock 数据开发页面，后端完成后只替换 API 地址。

## 7. `backend/`：后端服务

后端负责业务规则、数据库、MQTT 和权限。推荐先做成一个应用，内部再按模块分目录。

```text
backend/
├── src/
│   ├── modules/
│   │   ├── auth/                 # 登录、用户、角色
│   │   ├── farm/                 # 农场、地块
│   │   ├── device/               # 设备注册、绑定、在线状态
│   │   ├── telemetry/            # 温湿度数据和历史趋势
│   │   ├── command/              # 灌溉指令和执行结果
│   │   ├── alert/                # 阈值告警和告警记录
│   │   └── chat/                 # 智能问答接口
│   ├── mqtt/                     # MQTT 连接、订阅、发布
│   ├── websocket/                # 实时推送给前端
│   └── common/                   # 鉴权、异常、日志、公共工具
├── migrations/                   # 数据库建表和升级脚本
└── README.md
```

目录按业务分开，是为了让成员知道代码应该放在哪里。例如：

- 接收温湿度数据放 `telemetry/`；
- 发送灌溉命令放 `command/`；
- MQTT 连接细节放 `mqtt/`，业务模块不重复创建连接；
- 所有模块共用的登录校验放 `common/`。

## 8. `device-simulator/`：模拟设备

这个目录模拟真实硬件，帮助团队在没有硬件时完成开发和联调。

```text
device-simulator/
├── temperature-sensor/            # 定时上报温度
├── humidity-sensor/               # 定时上报湿度
├── irrigation-controller/         # 接收并执行开关指令
└── shared/                        # MQTT 客户端和公共消息模型
```

模拟设备必须严格遵守 `contracts/mqtt-topics.md`。后续换成真实鸿蒙设备时，只替换这里的程序，后端接口和前端页面不需要改变。

## 9. `ai-service/`：智能问答和 RAG

这个目录负责灌溉建议和农业知识问答，不负责普通设备管理。

```text
ai-service/
├── app/                           # 智能体接口和问答逻辑
├── knowledge-base/                # 农业知识文档
├── scripts/                       # 知识导入、向量化脚本
└── README.md
```

后端通过 HTTP 调用它。智能体可以读取经过授权的环境数据，但不应直接连接 MQTT；灌溉操作仍由用户确认后通过后端下发。

## 10. `database/`：数据库文件

```text
database/
├── schema/                        # 建表语句
├── seed/                          # 演示账号、农场、设备数据
└── README.md
```

- `schema/` 保证每个人建出相同的数据库；
- `seed/` 让新成员可以快速得到可运行的测试数据；
- 数据库脚本不应只存在某个人电脑里。

建议至少包含用户、农场、地块、设备、遥测记录、控制指令、告警规则和告警记录等表。

## 11. `infra/`：部署和运行环境

```text
infra/
├── docker-compose.yml             # 一键启动项目依赖
├── emqx/                          # EMQX 配置
└── nginx/                         # 前端和后端的统一入口（可选）
```

当前 `infra/docker-compose.yml` 里面只有 EMQX。后续可以把数据库、后端和前端逐步加入这个文件。

部署文件的目的，是让组员和演示环境使用相同的启动方式，而不是每个人手动安装不同版本的软件。

## 12. `tests/`：联调和测试

```text
tests/
└── integration/                   # 跨模块测试
```

这里重点验证完整流程，而不只是单个函数：

```text
模拟设备上报 → 后端接收 → 数据库存储 → 前端看到数据
前端下发指令 → MQTT → 模拟灌溉设备 → 结果回传 → 页面更新
```

这类测试可以证明各成员的代码真正连接成功。

## 13. 哪些文件现在必须先创建

第一阶段建议先创建这些文件：

```text
README.md
CONTRIBUTING.md
contracts/openapi.yaml
contracts/websocket-events.md
contracts/mqtt-topics.md
contracts/data-dictionary.md
database/schema/README.md
frontend/README.md
backend/README.md
device-simulator/README.md
ai-service/README.md
```

其中最优先的是 `contracts/`。只有接口格式先确定，前后端才能真正并行工作。

`ai-service/`、`nginx/` 和集成测试可以在基础监测和控制链路打通后再完善。

## 14. 一句话理解整个项目

```text
contracts/ 规定怎么说话
frontend/ 负责给用户看和操作
backend/ 负责业务判断和数据保存
device-simulator/ 模拟真实设备
ai-service/ 负责农业知识问答
database/ 保存系统数据
infra/ 负责把系统启动起来
tests/ 验证各部分能不能连起来
```

组长首先维护 `contracts/` 和 `docs/`；其他成员在自己负责的目录内开发，遇到接口变化先修改契约并通知团队，再同步修改代码。
