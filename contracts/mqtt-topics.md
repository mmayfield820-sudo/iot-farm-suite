# MQTT 主题与数据格式规范（对齐需求1）

> 

---

## 1. 总体策略：先脚本模拟，后接硬件

- **模拟阶段**：用 Python 脚本（模拟传感器发数据、模拟灌溉设备执行指令。
- **硬件阶段**：换成真实鸿蒙设备。
- **关键要求**（来自需求1）：**模拟设备和真实设备用「完全相同」的数据格式和 MQTT 主题**，只通过配置切换数据源。这样后期接硬件时，后端、前端一行不用改。

---

## 2. 命名规范（来自需求1，已确定）

| 对象                | 编号规则               | 示例           |
| ----------------- | ------------------ | ------------ |
| 用户 User           | U + 序号             | `U001`       |
| 农场 Farm           | F + 序号             | `F001`       |
| 地块 Plot           | P + 序号             | `P001`       |
| 设备 Device（内部ID）   | D + 序号             | `D001`       |
| 设备编号（业务编号）        | SENSOR + 序号（大写）    | `SENSOR-001` |
| 通信标识（MQTT 里识别设备用） | device + 序号（小写下划线） | `device_001` |

> 区分三个容易混的：**设备ID（D001）** 是数据库内部主键；**设备编号（SENSOR-001）** 是给人看的业务号；**通信标识（device_001）** 是 MQTT 主题和消息里用的。

---

## 3. 设备清单（模拟阶段 3 台，⭐建议值）

| 设备ID | 通信标识         | 设备编号         | 设备类型  | 作用     |
| ---- | ------------ | ------------ | ----- | ------ |
| D001 | `device_001` | `GH01-SOIL-001` | 湿度传感器 | 上报湿度   |
| D002 | `device_002` | `GH01-TEMP-001` | 温度传感器 | 上报温度   |
| D003 | `device_003` | `SENSOR-003` | 灌溉设备  | 接收控制指令 |

> 需求1 里设备类型是**分开的三种**（温度/湿度/灌溉），所以模拟器要模拟 3 台设备，不是 1 台发全部。本表是可调的建议值，A 可改。

---

## 4. MQTT 主题设计（⭐建议值，对齐需求1 用通信标识）

| 主题                               | 方向      | 用途             |
| -------------------------------- | ------- | -------------- |
| `farm/telemetry/{deviceId}`      | 设备 → 后端 | 传感器数据上报（温度/湿度） |
| `farm/status/{deviceId}`         | 设备 → 后端 | 心跳 / 在线状态      |
| `farm/command/{deviceId}`        | 后端 → 设备 | 控制指令下发（灌溉开关）   |
| `farm/command_result/{deviceId}` | 设备 → 后端 | 控制执行结果回传       |

- `{deviceId}` = 通信标识，如 `device_001`。
- 例：温度传感器发数据到 `farm/telemetry/device_001`；灌溉指令发到 `farm/command/device_003`。

---

## 5. 消息格式（JSON）

### ① 数据上报（遥测）—— 传感器每隔几秒发一条

```json
{
  "deviceNo": "SENSOR-001",
  "deviceId": "device_001",
  "type": "temperature",
  "value": 25.6,
  "msgId": "M00001",
  "ts": "2026-08-21T09:59:50"
}
```

| 字段         | 说明                                     |
| ---------- | -------------------------------------- |
| `deviceNo` | 设备业务编号（SENSOR-001）                     |
| `deviceId` | 通信标识（device_001，主题里也用这个）               |
| `type`     | 设备类型：`temperature`（温度）/ `humidity`（湿度） |
| `value`    | 数值（温度 ℃ 或 湿度 %）                        |
| `msgId`    | **消息编号**（单调递增，用于后端处理重复/乱序数据，需求1 要求）    |
| `ts`       | 采集时间（ISO 格式）                           |

### ② 心跳 / 在线状态 —— 每 10 秒发一条

```json
{
  "deviceNo": "SENSOR-001",
  "deviceId": "device_001",
  "online": true,
  "ts": "2026-08-21T09:59:50"
}
```

### ③ 控制指令下发 —— 后端发给灌溉设备

```json
{
  "commandId": "CMD0001",
  "deviceId": "device_003",
  "action": "irrigation_on",
  "ts": "2026-08-21T10:00:00"
}
```

| 字段          | 说明                                      |
| ----------- | --------------------------------------- |
| `commandId` | **唯一指令编号**（幂等/去重，需求1 要求）                |
| `action`    | `irrigation_on`（开）/ `irrigation_off`（关） |

### ④ 控制执行结果回传 —— 设备执行后回给后端

```json
{
  "commandId": "CMD0001",
  "deviceId": "device_003",
  "result": "success",
  "ts": "2026-08-21T10:00:02"
}
```

| `result` 取值 | 对应需求1 的页面状态 |
| ----------- | ----------- |
| `success`   | 执行成功        |
| `failed`    | 执行失败        |
| `timeout`   | 执行超时        |

> 需求1 明确：控制下发后页面显示「下发中→执行成功/失败/超时」，**不能发完就假定已执行**。所以必须有④这个回传主题，前端状态靠它更新。

## 6. 认证

- **暂不配账号密码**（匿名连接），保持最简单。
- 需求1 提到「密码加密存储、接口鉴权」是**后端接口层**的事，和 MQTT 的匿名是两回事，别混淆。
